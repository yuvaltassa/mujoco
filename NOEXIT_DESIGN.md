# Never exit: recoverable errors as an `mjtStatus` follow-up

*Design proposal, 2026-08-27. Branch `noexit`. Follow-up to [ONWARN_DESIGN.md](ONWARN_DESIGN.md).*

## Summary

The process belongs to the user: the library may fail, but only the user may terminate. Today
every `mjERROR` ends in `exit(EXIT_FAILURE)` unless a handler intercepts control, and the
handlers that do (the model compiler, the Python bindings) each hand-roll the same unwinding
machinery — incompletely. This proposal makes error recovery a property of the library:

1. **Error boundaries at public entry points.** Each fallible public function establishes a
   `setjmp` boundary in a thread-local boundary stack. `mju_error` delivers its message to the
   log handler as today, then — in never-exit mode — `longjmp`s **one hop** to the innermost
   boundary, which restores the invariants it snapshotted at entry and returns an error
   status.
2. **Errors surface through `mjtStatus`.** The value space reserved by the onwarn design is
   consumed: warnings occupy the low bits, hard errors report as `mjSTATUS_ERROR` (sign bit).
   `if (mj_step(m, d))` catches both; callers who care distinguish them. No new channel, no
   new plumbing — the propagation discipline already exists.
3. **Failed calls poison the `mjData`.** After an error return, a poison flag makes every
   subsequent pipeline call on that `mjData` return `mjSTATUS_ERROR` immediately, until
   `mj_resetData`. Recovery cannot be silently ignored.
4. **Default unchanged.** Never-exit mode is an explicit global opt-in
   (`mju_setNoExit(1)`); the default remains termination. A process that ignores error
   returns should die loudly, not proceed quietly.

This is *never exit*, not *never error*: `mjERROR` sites are untouched and remain the raise
mechanism; what changes is who decides whether the process survives.

## Error taxonomy and recovery contracts

`mjERROR` sites fall into three classes with different post-recovery guarantees:

| class | examples | contract after error return |
|---|---|---|
| input validation | unknown solver type, unsupported integrator combination, bad function arguments | state untouched; call again with fixed inputs |
| resource exhaustion | `mj_stackAlloc` overflow, arena misuse beyond the CNSTRFULL saves | state partial through the failed stage; stack/arena pointers restored by the boundary; reset or resize and retry |
| invariant violation | "nefc mis-allocation", "BVH stack depth exceeded", SHOULD-NOT-OCCUR checks | **data poisoned**; the only supported operations are inspection, `mj_resetData`, `mj_deleteData` |

The third class is why "never error" is unachievable: a failed invariant check means the
library no longer knows what state it is in, and no mechanism can promise otherwise. What it
*can* promise — because these checks fire before the write they guard — is that the damage is
confined to the poisoned `mjData`/`mjModel`, and that the process, and every other model and
thread in it, continues. For a robotics process, reinitializing a controller beats dying.

## Mechanism

### The boundary

A boundary is a snapshot plus a jump target, in a thread-local stack:

```c
typedef struct mjErrorBoundary_ {
  jmp_buf env;
  mjData* d;                     // NULL for functions without mjData
  size_t pstack, parena;         // restore points
  struct mjErrorBoundary_* prev;
} mjErrorBoundary;
```

The wrapper of a fallible public function pushes a boundary, snapshots `d->pstack`/`d->parena`,
and calls the implementation. On `mju_error` in never-exit mode, the default handler (after
formatting and delivering the `mjLogMessage` exactly as today) pops the innermost boundary and
`longjmp`s to it; the wrapper restores the snapshot, sets the poison flag for
invariant-class errors, and returns `mjSTATUS_ERROR`. On the normal path the wrapper pops and
returns the implementation's status unchanged.

One hop is all that is ever needed: from the boundary outward, the ordinary `mjtStatus`
returns introduced by onwarn carry the failure. The step path performs no heap allocation —
mjData stack and arena are the only resources in flight — so the snapshot *is* the cleanup.
This also fixes a latent bug that exists today: when the Python bindings convert a mid-step
`mjERROR` into `FatalError`, nobody restores `d->pstack`; catch the exception, keep the
mjData, and you have leaked stack. Only the library can restore its own invariants at the
boundary, which is why this belongs in the library and not in bindings.

### Hiding the wrappers (and keeping the docs honest)

The documentation links every function name to its implementation on GitHub
(`linenumbers.js`, generated by scanning sources for textual `type name(...) {` definition
lines). A hand-written `mj_step` wrapper would hijack that link onto boilerplate. The
wrappers must therefore be invisible in source, which fixes the implementation technique:

- A generated *rename header*, force-included when compiling the engine library
  (`-include` / `/FI`, engine targets only), maps each fallible public name to its
  implementation symbol: `#define mj_step mj_step_impl` …
- The implementations are **textually unchanged**: `engine_forward.c` still reads
  `mjtStatus mj_step(const mjModel* m, mjData* d) {` at the same line, so the documentation
  link, blame, and readability are untouched. The macro renames the *symbol*, not the source.
- A single generated boundary file (compiled without the rename header) defines the public
  symbols as X-macro invocations: `MJ_BOUNDARY(mjtStatus, mj_step, ...)`. These lines do not
  match the scanner's definition regex, so the wrappers are invisible to the docs by
  construction; the file is likewise excluded from formatting-sensitive tooling.
- Wrappers are trivial by construction (no locals live across `setjmp`), which is also what
  makes them immune to the setjmp-volatile trap.

The rename has a second, deeper consequence: **internal calls bypass the boundaries**.
Engine code calls `mj_forward_impl` directly, so there is exactly one active boundary per
user-level call — one `setjmp` per API entry, zero cost inside the pipeline — and the
foreign-frame rule enforces itself: external code (user callbacks, plugins) can only enter
the engine through public symbols, and every public symbol is a boundary. An `mjERROR` raised
by engine code called from inside `mjcb_control` is caught at that inner boundary and
returned to the callback as a status; the unwind never crosses a foreign frame, so the
undefined behavior of `longjmp` through C++ destructors cannot occur.

### Worker threads

`longjmp` across threads is undefined; worker-thread errors need their own boundaries. The
engine has exactly three `mju_dispatch` sites, and the task runner is the natural per-worker
boundary: `setjmp` at task entry, record the error in the task slot, return from the task
normally; the join aggregates and the calling thread returns the error through its own
boundary. This closes a hole that exists today independent of this proposal: a worker-thread
`mjERROR` (e.g. the SHOULD-NOT-OCCUR check in `collisionTask`) bypasses the bindings'
thread-local handler and exits the process even under Python.

### Mode, platforms, bindings

- `mju_setNoExit(int enable)`, process-global, default off. With the mode off the wrapper is
  a flag check and a tail call — no `setjmp` executes, cost is a branch.
- WASM: `setjmp` requires `-sSUPPORT_LONGJMP` under Emscripten, with measurable overhead;
  the wasm build ships with the mode compiled out until someone needs it.
- Windows: `longjmp` over C frames is well-defined with MSVC; the boundary file is C and the
  foreign-frame rule keeps C++ frames out of the unwind path.
- Python bindings: replace the bespoke error-to-exception machinery for pipeline calls with
  the library boundary — enable never-exit mode and raise `FatalError` from an
  `mjSTATUS_ERROR` return, preserving the user-facing API while gaining correct stack
  restoration. Load-time errors keep the existing compiler path, which already recovers.

## Phasing

1. **Runtime pipeline**: the onwarn-converted functions plus the remaining public runtime
   functions that transitively reach an `mjERROR` (enumerated with the same transitive-caller
   audit used for warnings). Restore = the two-field snapshot; poison flag in `mjData`.
2. **Dispatch boundaries**: the three task runners; per-task error slots; join aggregation.
3. **Creation and I/O functions** (`mj_makeData`, `mj_copyData`, `mj_loadModel`, …): these
   allocate, so boundaries need real cleanup paths; they already have NULL-return
   conventions to slot into.
4. **Excluded**: `mjr_` (a GL context mid-mutation is not restorable by snapshotting two
   integers), and errors raised *by* plugins (plugins are foreign frames; they get the
   status like any caller).

## Testing

The real cost of this design is the error-injection harness, and it is also the payoff:

- A test hook forcing each `mjERROR` site to fire (site enumeration from the audit; injection
  via a test-only callback checked by `mjERROR` in debug builds).
- Per-site invariants: boundary returns `mjSTATUS_ERROR`; `pstack`/`parena` restored to the
  entry snapshot; poison set exactly for invariant-class sites; `mj_resetData` fully
  recovers; ASAN/MSAN clean across the unwind.
- A soak test: randomized error injection during long rollouts, asserting the process
  survives and post-reset trajectories are bit-identical to never-errored runs.

## Open questions

1. `mjtStatus` encoding for errors: sign bit (`status < 0` = error, `> 0` = warnings, `0` =
   OK) vs. a dedicated high bit; whether the error value carries a small error-class code.
2. Error message retrieval beyond the log handler: is the handler enough, or add a
   thread-local `mju_lastError()` query?
3. Poison granularity: pipeline calls only, or every mjData-taking function?
4. Whether `mj_forward`-in-callback re-entry under never-exit mode needs a re-entrancy guard
   on the boundary stack (believed unnecessary: the stack nests naturally).
5. Naming: `mju_setNoExit` vs. folding into `mjLogConfig`.
